# 答辩教师提问回答（二）：最小可行系统、降级方案与AI辅助开发的责任归属

> 对应问题：本项目同时涉及大语言模型、语音识别、声学分析、视觉分析、跨模态融合、RAG、Agent和前后端系统。请明确最终必须完成的最小可行系统以及可以删减的扩展功能；如果本地大模型、视觉分析或实时三模态融合未能达到预期，你将采用什么降级方案？在使用Codex等生成式AI辅助开发的情况下，你将通过哪些代码说明、版本记录、测试材料和现场修改能力证明自己能够理解、调试、维护并对最终系统负责？

## 一、最小可行系统与可删减功能

### 1.1 MVP 定义：一个完整的 Agent 闭环

我的最低交付标准是：**"打开页面 → 选岗位 → Agent出题 → 候选人回答 → 系统分析 → Agent决定下一题 → 多轮循环 → 生成报告"这个闭环必须完整可运行。** 答辩演示时，老师看到的是一个"活的"系统，不是一个PPT。

MVP 必须包含的模块：

| 必须（P0） | 说明 | 当前状态 |
|---|---|---|
| 前后端可运行 | Next.js + FastAPI，能跑通完整对话 | ✅ 已实现 |
| Agent 决策引擎 | 状态机 + 四条决策路径（深挖/转题/提示/结束） | ✅ 已实现，7条优先级规则 |
| 文本 5 维分析 | 关键词覆盖、结构逻辑、术语准确、简历匹配、信息密度 | ✅ 已实现（关键词匹配 + 结构信号检测） |
| 知识库 RAG 检索 | 按岗位+维度检索知识点，注入 Agent 出题上下文 | ✅ 已实现（501条，JSON内存加载） |
| 报告生成 | 18维评分 + 雷达图 + 优缺点 + 学习路径 | ✅ 已实现 |
| MockLLM 出题 | 用结构化题库替代真实 LLM，确保可演示 | ✅ 已实现 |

### 1.2 可降级/可删减模块

| 可降级（P1/P2） | 降级策略 | 理由 |
|---|---|---|
| **ChatGLM-6B 真实部署** | 当前 MockLLM 已可演示完整闭环，答辩时能说明架构设计能力即可 | 本地部署6B模型硬件要求高（16GB+显存），且推理延迟可能超过3秒要求 |
| **MediaPipe 实时面部分析** | 降级为浏览器端模拟数据（当前已实现），接口保留，通过 face_data 字段传模拟值 | 浏览器端 WASM 加载不稳定，CDN资源不可控；18维评估管道本身不受影响 |
| **Whisper 语音转文字** | 降级为 Web Speech API（浏览器内置）+ 模拟声学分析数据 | Web Speech API 零部署成本、准确率高，符合隐私合规（不上传服务器） |
| **librosa 声学特征分析** | 降级为 VAD 能量检测 + 停顿计数（当前已实现），韵律分析用模拟数据 | 真实 librosa 需要服务器端处理音频流，增加架构复杂度和延迟 |
| **ChromaDB 向量检索** | 降级为 JSON 内存加载 + 关键词匹配（当前已实现） | 500条知识点规模下内存检索足够快（<50ms），向量检索是架构预留而非必须 |

**一句话总结**：核心创新（Agent 决策引擎）必须 100% 完成；真实 LLM 和真实多模态感知是"加分项"，能用降级方案证明架构设计的正确性。

## 二、降级方案（三层防御体系）

我为本系统设计了三层降级防御，确保无论哪个环节出问题，系统整体都能运行。

### 第一层：LLM 降级

| 场景 | 降级方案 | 架构保障 |
|---|---|---|
| ChatGLM-6B 部署失败/推理超时 | MockLLM 题库接管（当前方案），5岗位 × 4策略 × N变体，random.shuffle 打乱 | `BaseLLM` 抽象接口，一行配置切换 |
| MockLLM 题库耗尽 | 通用提示语兜底（如"请继续说说你的理解"） | MockLLM 内置通用话术 |
| 需要真实 LLM 时 | 调用 OpenAI 兼容 API（ChatGLM/DeepSeek 均可），只需改环境变量 | `ChatGLMClient` 已实现，只需填 API URL |

### 第二层：多模态感知降级

| 场景 | 降级方案 | 架构保障 |
|---|---|---|
| MediaPipe WASM 加载失败 | `simulateFaceData()` 生成模拟面部数据，18维视觉4维用模拟值评分 | 独立 try-catch，失败不阻断主流程 |
| 摄像头权限被拒绝 | 视觉分析模块静默降级，视觉4维返回中性分50分，不参与融合决策 | 前端 FaceCapture 有状态机（未开启/采集中/异常/权限拒绝） |
| Web Speech API 不可用 | 文本输入为主通道，语音为辅助通道 | 对话输入框始终可用 |
| 任一感知管道异常 | 融合层自动调整权重——出问题的模态权重降为0，其他模态权重按比例放大 | 融合层已实现 modality_scores 独立计算 |

### 第三层：融合层降级

| 场景 | 降级方案 |
|---|---|
| 三模态全正常 | 18维完整评估 + 跨模态一致性分析 |
| 两模态正常 | 缺失模态维度填中性分50，融合层仅分析可用模态 |
| 仅文本正常 | 系统退化为"文本5维 + Agent决策"模式，这恰好是MVP的核心路径 |
| 任何模块崩溃 | FastAPI 全局异常捕获，返回 200 + 降级标记，不报 500 |

**关键设计理念**：**决策与感知解耦**——Agent 决策引擎只依赖"18维分数向量"这个抽象接口，不关心分数是从真实分析来的还是模拟的。这意味着感知层的任何降级对 Agent 决策层完全透明。

## 三、AI 辅助开发下的责任归属证明

我使用 Codex 等 AI 工具辅助开发，但我通过以下五个方面证明系统是我的作品、我能对其负责：

### 3.1 架构设计归我，代码生成归 AI

AI 帮我做的事：写样板代码（如 FastAPI 路由模板、Tailwind CSS 布局）、生成 Mock 数据、格式化输出。

我自己做的事：
- **系统架构设计**：三层架构（感知→融合→决策）是我提出的
- **18 维评估体系设计**：维度定义、权重分配、评分算法都是我设计的
- **Agent 决策规则**：7 条优先级规则的决定逻辑和参数阈值（如连续3轮<35分结束、weak_count≥3转话题）是我根据面试场景分析后确定的
- **知识库结构**：5岗位×6话题的分类体系是我规划的

### 3.2 代码层面的理解证明

我对关键代码了如指掌，能现场回答任何实现细节：

- `agent.py` 的 `DecisionStrategy.decide()` 方法：7条规则按优先级排列，从"已标记结束"到"默认深挖"，每条规则对应一个具体的面试策略判断
- `fusion.py` 的跨模态一致性算法：用三模态得分的标准差来衡量一致性，标准差越大说明候选人的语言表达和身体语言越不一致
- `llm.py` 的 MockLLM 两层索引结构：`_shuffled[session_id][decision_type]` 确保同一会话内不重复、不同会话间打乱
- 前后端交互：前端传 session_id + position + messages，后端依次跑 text_analysis → voice_analysis → visual_analysis → fusion → agent_decision → knowledge_retrieval → llm_generate，7步编排

### 3.4 可现场证明的调试能力

答辩时，我可以现场做以下操作来证明我对系统的掌控：

1. **实时修改 Agent 决策规则**：比如把"连续3轮<35分结束"改成"连续2轮<40分结束"，重启后端，立即看到面试行为变化
2. **切换 MockLLM / ChatGLM**：改一行代码，展示架构的灵活性
3. **注入异常场景**：关闭一个分析管道，展示降级机制如何自动调整
4. **查看 Agent 状态日志**：展示每轮面试的 decision、pressure_level、weakness_hits，证明我理解状态追踪
5. **修改知识库数据**：增删一条知识点，展示 Agent 出题内容如何跟随变化

### 3.5 最终责任声明

我理解并同意：使用 AI 工具是"提效手段"而非"替代思考"。本系统的以下核心部分**由我独立完成设计决策**：

- 为什么选状态机而非强化学习做 Agent 决策？因为面试策略需要可解释性，状态机的每一条规则都可以溯源
- 为什么 18 维分四组？因为文本、语音、视觉是三个独立模态通道，融合层处理跨模态关系
- 为什么视觉分析放浏览器端？因为隐私合规——候选人视频不上传服务器
- 为什么 RAG 先做 JSON 不做 ChromaDB？因为 MVP 阶段数据量小（500条），内存检索更快更稳定

**我能对系统的每一行代码、每一个设计决策、每一个降级方案做出解释。AI 帮我写代码，但架构思路、技术判断、创新点和责任归属始终在我。**
